# AtomForge 团队协作与双层看板 · delivery-v1

本文同时给出当前实现、运行规则、评审模板和后续接入标准。不能将“设计方案”当作已存在的自动化能力；每种门禁的证据强度在下文标明。

## 1. 现状问题与假设

代码检查发现：原看板是阶段流水线，并非完整战略/交付双层看板。领导可以调整设计与架构的顺序，专业角色例行交接给领导，测试失败还要多调用一次领导模型才能修复。阶段名、角色、状态混在一起，难以稳定统计。

替代方案：固定状态机 + 工作包卡片 + 可版本化战略策略。角色直接交接，领导只在开始设定策略，以及范围冲突、资源不足、外部依赖、修复耗尽时介入。

本版假设与边界：

- 默认团队六位成员分别承担领导、产品、设计、架构、开发、测试；领导始终展示在首位。自定义团队保留已选成员，不偷偷补人。
- 一个 StudioRun 是一个增量交付批次，拆成五个专业工作包。工作包卡片包含该阶段全部检查项，一卡一个负责人；不要把多个可以独立验收的需求长期塞进一个批次。
- 现有执行器每次执行一个专业工作包，同一账号一次只有一个生成任务。此版不声称实现多项目抢占或模型并行。提高 WIP 上限只提高允许容量，不自动增加资源。
- 正式交付指保存可运行的 AtomForge 版本，不等于公网部署。付费、公开发布、不可逆外部操作继续走各自明确授权入口。
- 暂无生产缺陷登记和发布批次关联，缺陷逃逸率显示“暂无数据”，不能以零代替。
- 需求、设计、架构的自动门禁目前是结构检查与必要问题确认。专业内容的独立签审采用第 5 节模板；尚未接入独立签审自动拦截，不把它标为已完成的同行评审。

## 2. 角色接口与交接

|角色|唯一职责边界|直接交互对象|必须输出|何时升级领导|
|---|---|---|---|---|
|领导 Atlas|目标、优先级、容量、资源安排、SLA、门禁强度和例外；不逐卡转发、不替测试通过|产品；需要协调的专业负责人；用户|一次阶段计划、工作包分工、战略策略、调整原因|自己承担升级处理，涉及用户真实业务选择再询问用户|
|产品经理 Milo|澄清问题、范围、不做什么、可验证 AC；确认业务结果|用户、设计、测试|需求说明、工作包检查项、验收标准、必要决策|范围冲突、缺少业务规则、必须由用户决定的条件|
|交互设计师 Luna|页面层级、用户路径、空/错/加载状态、响应式行为|产品、架构；实现问题直接找开发|交互规范、状态矩阵、设计取舍|体验目标与预算/范围无法兼容|
|技术架构师 Ollie|组件与文件边界、数据/API 契约、风险、实现顺序|设计、开发；可测试性找测试|技术方案、契约、风险和迁移/回退说明|新增外部服务、成本或破坏性变更|
|应用工程师 Neo|按已确认方案增量实现、开发自测、复现并修复缺陷|架构、设计、测试|变更文件、草稿、自测步骤、构建日志|达到配置的修复上限仍无法通过，或发现范围/外部依赖问题|
|测试工程师 Pip|独立审查源码、基于 AC 编写交互测试、核实实际执行结果|产品确认 AC；直接向开发开缺陷|审查结论、复现信息、独立测试、执行证据|修复上限耗尽或验收标准矛盾；不得自行扩大范围|

正常顺序：领导一次设定目标 → 产品 → 设计 → 架构 → 开发 → 测试 → 保存交付。领导最后向用户汇总真实结果，无需额外“通过审批”模型调用。

返工顺序：测试失败 → 原始错误/复现证据直接交开发 → 修复 → 重新构建和独立测试。没有新事实不重复找领导，不重复询问用户已回答的问题。

协作者只补充本岗位相关证据，不能另起一条无主任务。建议先进入对应专业工作包的交接上下文，不把领导当消息中转站。高成本额外会诊应由具体问题触发。

后续并行化条件：产品 AC 冻结后，设计初稿与架构风险预研可并行；完整实现仍需两者契约一致。只有执行器支持任务取消、隔离上下文、并发预算和合并冲突检查后再开启，不能只调整看板 WIP 就声称并行。

## 3. 固定交付看板

固定列及机器标识：**待办 backlog → 就绪 ready → 进行中 doing → 评审中 review → 验证中 verifying → 待验收 acceptance → 完成 done**。

文档工作包通过结构门禁后允许 review → done；代码工作包必须经过实际验证和保存验收。正常缺陷允许 review/verifying/acceptance → doing。阻塞不是新列，不改变状态 ID。

|列|负责人|准入（DoR）|准出|输出物|允许下一状态|
|---|---|---|---|---|---|
|待办|该卡唯一专业负责人；产品维护范围|已登记目标、检查项、输出物、依赖和负责人|依赖满足；无未处理的范围冲突|工作包卡片|就绪|
|就绪|该卡负责人|上游交接完成；AC、必要上下文可获取|负责人拉取且进行中数量不超 WIP|本次执行上下文|进行中|
|进行中|该卡负责人|DoR 满足；资源可用|文档或真实源码已保存；失败不得伪造输出|文档/代码草稿|评审中|
|评审中|卡片负责人负责补充和修订；专业接收人/QA 提供审查|产出可读取、契约可验证|文档结构门禁通过；代码进入独立审查和执行验证|结构校验或独立审查结果|文档完成；验证中；返工进行中|
|验证中|开发卡由开发负责修复，测试卡由 QA 负责验证|审查记录、代码、自测/独立测试输入齐备|实际执行通过，必要断言覆盖核心行为|真实日志、失败复现信息|待验收；返工进行中|
|待验收|开发负责版本交付，产品对业务 AC 负责，QA 提供证据|独立审查和浏览器测试通过|版本基线仍一致，保存成功|版本号、代码、预览产物、测试报告|完成；返工进行中|
|完成|原唯一负责人保持不变|DoD 已满足且证据可追溯|不继续叠加新范围|归档工作包|无；新需求另开批次|

通用 DoR：目标、边界、唯一负责人、检查项、AC、输出物和依赖明确；不把纯配色偏好当阻塞。产品卡可以负责补齐业务 AC，后续卡从已确认产品文档继承 AC。

通用 DoD：检查项有对应产出；所需门禁有真实证据；必要阻塞已解决；项目归属和基线保持一致；不得把“模型说已通过”当作执行日志。

泳道：标准 / 加急。低优先级仍在标准泳道，保留 priority=low。当前策略作用于本轮批次，不跨账号抢占执行资源。加急必须记录原因，不跳过 AC 或测试。

WIP：当前实现限制 doing 列总量，默认 1，可设 1–3；其他列不设伪装成已执行的限额。建议扩展团队后将 review、verifying、acceptance 各限制为 1，先清理下游再拉取上游。增加列级 WIP 需新增策略字段与对应准入检查，不改状态 ID。阻塞卡继续占用原列容量。

卡片字段：id、role、owner（智能体 ID）、owner_name、collaborators、title、tasks、acceptance、output、depends_on、state、blocked、evidence、created_at、history、lane、cycle_seconds、overdue。

ID：`<run_id>:w<需求迭代号>:<role>`。范围修订归档旧卡并新建迭代 ID；单纯战略调整保持卡片 ID。每个检查项都属于一个工作包，不允许隐藏在私聊中不记录。

## 4. 自动触发、阻塞与恢复

|事件|系统动作|失败处理|
|---|---|---|
|领导计划验证通过|固定排序，创建/恢复五个工作包；填入成员快照|格式修正；仍无效则保留任务错误|
|上游交接条件满足|待办 → 就绪|依赖缺失留在待办|
|角色模型调用前|就绪/返工 → 进行中，核验依赖与 WIP|禁止越过依赖，不虚报开工|
|文档或代码真实产出保存|进行中 → 评审中|无产出则保留草稿和错误|
|出现必要业务决策|在当前评审列标记阻塞、交给具体负责人询问|外部条件和不可逆事项不自动同意|
|文档契约有效、必要问题解决|产品/设计/架构卡完成，下游可拉取|结构失败自动修正；实质签审见下一节|
|代码及开发自测已保存|开发卡进入验证；QA 卡在代码交接后可开始|开发自测失败直接回开发，不找领导重述|
|QA 独立源码审查通过|验证 QA 编写的测试|审查拒绝/测试不足直接形成返工证据|
|真实独立测试通过|QA 卡完成；开发卡进入待验收|任一步失败，禁止保存正式版本|
|保存基线版本成功|开发卡完成，周期结束|版本冲突/保存失败不得显示完整交付|
|修复超过策略上限|保留草稿、记录错误，升级领导|不无限重试；可调整范围或恢复任务|
|策略修改|revision +1，记录前后值与原因；后续门禁读取新值|过期 revision 返回 409；禁止覆盖其他人更新|

QA 的“就绪”条件是开发已交接代码，不要求开发先“完成”，避免开发等测试、测试又等开发的循环依赖。

现有重试保留已产出的需求/设计/架构；基线版本未变且代码草稿已保存时，先复用代码继续验证，验证失败确认需改代码后才调用开发，不一律重写。确认卡恢复和服务重启继续使用持久化状态。历史任务没有 v1 卡片数据时继续显示历史流水线，不伪造迁移时间。

### 测试问题与应用缺陷分流

交接文案与业务门禁分离：`handoff` 完整保存在交接文档并传给下游，不再按 400 字硬校验。对话消息仅显示最多 400 字的预览，长内容可展开查看。模型应尽量用 80–160 字交接，将详细契约写入正文；这是表达建议，不是中断任务的条件。必需的需求字段、类型和真实测试门禁继续校验。

- 构建或业务结果断言失败：保留真实证据，按应用修复流程处理；不自动修改预期来消除红灯。
- 交互操作或协议失败：每轮最多一次额外 QA 诊断，只允许输出原因与测试步骤，不允许代码补丁。需引用需求和源码证明测试有错；例如空白输入使按钮合法禁用，应断言 `disabled`，不能点击该按钮或取消业务校验。修正必须保留原验收目标，并记录原步骤、替代步骤、原因和失败信息。
- 修正的测试必须对同一份源码实际重跑，随后仍需通过独立 QA；不跳过步骤、不直接将失败改为通过。仍失败则进入有限的代码修复路径，默认最多 30 轮修复重测（可在战略看板设为 0–30 轮），另有首次验证；提前通过立即交付，耗尽仍失败则保留草稿，不能以重试次数代替实际验收。测试脚本修正不计入开发返工。旧任务继续执行时，未调整过策略的旧默认 2 轮预算升级为 30 轮；已记录的策略调整及新版本明确设置的较低预算保持不变。
- 开发自测覆盖不足由 QA 补充独立测试，不直接要求重写应用。QA 的 `approved` 表示源码审查通过，只有独立执行成功后 `verified` 才为真，不能声称执行过未运行的用例。
- 动作协议：`click/fill/text/visible/hidden/enabled/disabled/reload/clear_storage`，最多 48 步；最后一步为结果断言。`reload`、`clear_storage` 不需要 selector，后者只清空隔离测试环境的 localStorage，需显式 reload 才重新加载 UI。每次构建使用全新隔离浏览器，刷新保留该轮真实 localStorage，网络与 WebSocket 仍被拦截；云接口仍是测试替身，不能作为真实云服务验收证据。
- 持久化测试模板：正常添加 → 打卡 → 检查完成率 → reload → 检查数据与完成率 → 删除 → reload → 断言空状态。禁用校验模板：fill 空白 → disabled → fill 有效值 → enabled → click → 结果断言。不得在交付代码中插入测试按钮、调试模式或绕过业务的入口。

## 5. 评审门禁与证据等级

|门禁|提交者 → 接收/审查者|具体检查项|拒绝条件|本版自动化边界|
|---|---|---|---|---|
|需求|产品 → 设计；QA 核对可测试性|目标、范围、不做清单、AC、依赖；现状缺陷不能误当限制|AC 不可验证、业务规则冲突、必要依赖未知|JSON 字段校验、必要问题确认已实现；独立专业签审用模板登记，尚未自动拦截|
|设计|设计 → 架构；开发确认可实现性|主要路径、空/错/加载态、移动端、交互约束|关键交互缺失、与 AC 矛盾、无法实现|结构校验已实现；不能将此等同视觉或可用性评审通过|
|架构|架构 → 开发；QA 核对可测试性|文件/组件职责、数据契约、允许依赖、状态持久化、回退|契约冲突、未获准外部服务、破坏原有功能|结构校验已实现；成本/安全/迁移独立签审需模板证据|
|代码|开发 → QA|实际源码对照 AC、开发自测、构建、未涉及功能保留|编译失败、真实功能缺失、审查不通过|独立模型源码审查与真实构建已实现|
|测试|QA 独立执行|核心操作、实际结果断言、步骤数达到策略门槛|测试未运行、最后一步无结果断言、真实执行失败|独立浏览器测试已实现；不得只验证标题可见|
|验收|QA 提供证据，产品核对 AC，开发保存版本|业务结果与已确认需求一致；测试通过；基线保存成功|必要问题未解决、QA 未通过、版本冲突|保存前代码/QA 证据门禁已实现；独立业务签字尚未自动化；公网发布仍单独授权|

证据等级：L0 建议 → L1 结构有效的方案 → L2 独立审查 → L3 真实执行通过 → L4 版本保存。看板必须标出实际等级，不允许领导将 L1 直接升级为 L3。

专业签审接入方式：在下游已有模型调用中增加 `upstream_review`，包含 input_card_id、approved、issues、acceptance_mapping；无需为每个阶段增加领导调用。高风险变更要求专门角色签审，普通变更保留既有调用即可。上线前必须将缺少签审视为未通过，并补齐恢复和兼容测试；未上线前用下方模板记录，不能宣称强门禁已执行。

## 6. 领导战略看板

可动态调整：priority（urgent/normal/low）、doing WIP 1–3、SLA 1–1440 分钟、自动修复上限 0–30（默认 30）、独立测试最少步骤 2–16。既有实际测试动作最多 48 步的约束不变。

调整入口：任务看板的“领导战略看板”，或向领导明确提出“只调整策略，不改需求”。领导通过 strategy 动作更新同一策略记录，不走实施重规划。

不可调整：列和状态标识、独立测试必须执行、真实构建必须通过、归属权限、当前版本基线、已执行证据、当前任务成员快照。人力/智能体资源调整通过“我的团队”作用于下一次任务，避免在途任务换身份。

策略生效：优先级和 SLA 标记即时更新；WIP 在拉取时校验；修复上限在失败边界读取；测试门槛在执行独立测试前读取。刚执行完的门禁保留其证据，不因之后调整策略伪造重测。普通策略调整不清空代码、文档或已完成卡片。

领导自身战略卡建议字段：目标/受影响批次、问题、当前指标、拟调整字段、原值→新值、依据、观察窗口、回退条件、负责人、policy revision。状态固定为“观察 → 决策 → 生效观察 → 关闭”，与交付状态机分别版本化。当前 UI 实现为策略表单及变更记录，未实现独立战略卡拖动引擎。

## 7. 度量定义与采集

|指标|精确定义|采集来源/当前状态|使用方式|
|---|---|---|---|
|工作包周期时间|首次进入 doing 到 done，包含等待和返工|卡片 history；已展示，历史无起点则为空|同时看中位数与 P85，不只看平均|
|交付批次周期|创建工作流到所有卡完成|created_at/finished_at；已展示|与模型/构建耗时分开，避免把排队全算成模型慢|
|吞吐量|固定窗口内完成的交付批次数；工作包完成数另计|run 状态 + 完成时间；跨批次汇总待接入|按日/周观察，不把五张卡当五个功能|
|阻塞时间|blocked 设置到解除的时间区间之和，不重复计算重叠|卡片 history 已记录；跨卡统计待接入|按业务决策、外部条件、环境故障分类|
|返工率|发生至少一次 review/verifying/acceptance → doing 的已启动工作包数 / 已启动工作包数|history 可计算；当前 UI 显示开发返工次数|同时看次数与原因，不能用循环次数当工作包数量|
|缺陷逃逸率|交付后确认缺陷数 / 同发布批次全部确认缺陷数|需生产缺陷登记 + 版本关联；当前为空|分严重度；分母为零/缺少样本显示 N/A|
|门禁一次通过率|首次尝试通过门禁的工作包数 / 尝试该门禁工作包数|审查及构建事件可采集；汇总待接入|判断返工发生在需求、实现还是测试设计|
|领导介入成本|领导模型调用次数、tokens、耗时；单列真实例外处理|已有 StudioUsage + 阶段记录|普通修复不再调用领导模型；比较同规模任务|
|SLA 超时|未完成工作包当前周期 > policy.sla_minutes|已展示|是提醒，不是自动通过或自动放弃|

初始 SLA 15 分钟只是可修改的试运行假设，不是对模型速度的承诺。试运行至少收集 20 个同类批次，再以 P85 更新目标；不要凭一轮任务承诺提升百分比。

## 8. 变更机制

1. 专业负责人或领导提出变更卡：问题、证据、影响、迁移、回滚、自动化测试。
2. 数值策略通过带 revision 的补丁调整，必须有原因；策略冲突返回 409。任务结束后策略只读。
3. 主干状态新增/删除、依赖语义或门禁语义改变属于流程版本变更，不允许领导即时改。
4. 默认每两周回顾一次流程；安全/数据风险可紧急处理，但仍需版本和回退方案。频率是假设，可按实际团队节奏调整。
5. 新流程先影子计算、再用于新任务；在途任务固定版本，旧历史保留。不得修改历史卡片 ID 来迁就新 UI。
6. 自动化依赖 state ID、role ID、workflow version、policy revision 和 card ID，不依赖中文列名或领导生成的标题。
7. 提交前验证：合法/非法状态迁移、依赖、WIP、权限、并发策略覆盖、任务恢复、测试失败禁止交付、范围修订归档。

本版 API：`GET /api/v1/studio/runs/{id}` 的 `result.workflow` 返回列、卡片、策略、记录和指标；`PATCH /api/v1/studio/runs/{id}/strategy` 更新策略。没有允许浏览器随意拖到“完成”的接口，完成状态只能由真实执行门禁推动。

## 10. 落地顺序与验收

本次代码落地：领导展示首位、固定专业顺序、直接交接、去掉例行修复领导调用、持久化工作包状态、双层看板 UI、战略策略及版本冲突保护、真实测试底线、周期和返工记录。普通策略调整和需求重规划采用不同入口。

接下来按依赖顺序扩展，不能对尚未实现能力宣称完成：

1. 用真实任务验证默认策略与错误恢复，保留基线调用次数和耗时；观察六人默认团队及自定义团队。
2. 接入专业签审 `upstream_review` 与 AC→测试映射，再将需求/设计/架构/业务验收升级为强制独立门禁。
3. 增加生产缺陷登记与发布批次关联，生成周期 P50/P85、吞吐量和缺陷逃逸率。
4. 引入按契约并行的设计/架构预研；增加并发资源预算与取消测试后，才提高真实执行并发。
5. 跨任务排队器支持依赖就绪、优先级、SLA、饥饿保护后，再启用跨批次加急调度。主干 state ID 保持不变。

关键验收：正常一轮仅一次领导计划模型调用；普通测试失败直接进入开发修复；任意测试失败不保存正式版本；更改策略不清空产出；旧任务历史可读；每张实际工作包卡有唯一负责人、固定状态、输出物和证据。
