产品目标与体验路径

让应用想法不止停留在对话或代码片段：描述需求、看见真实结果、在浏览器操作、继续修改，最后交付可访问链接。优先打通“创建 → 生成 → 验收 → 版本 → 发布”，再补齐账号隔离、失败恢复与团队交互。目标是小规模可评审的工作台，暂不追求任意技术栈或商业平台的全部能力。

  1. 注册进入工作台，在“我的团队”查看默认六角色，也可创建团队并自由组合成员。
  2. 选择团队模式，输入“薄荷绿的每周习惯打卡，支持新增、七天切换、删除、完成率、刷新后恢复”。
  3. 观察专业角色交接，在固定交付看板查看负责人、任务、依赖和门禁；战略面板调整策略需填写原因。
  4. 完成后实际添加习惯、打卡并刷新，可在文件页查看或编辑源码，继续提出修改。
  5. 从“发布与部署”发布站内链接或导出工程；GitHub/Gitee/Netlify 功能需连接自己的第三方账号。

任务使用真实模型额度，时长受需求与服务影响。失败后可展开诊断并继续已有草稿，未验收代码不会冒充正式版本。

实现思路与关键取舍

固定交付流程，领导处理策略和例外

默认成员是 Atlas（领导）、Milo（产品）、Luna（设计）、Ollie（架构）、Neo（开发）、Pip（测试）。领导展示在首位，专业角色按依赖直接交接；普通返修由测试直接交给开发。

交付列固定为待办、就绪、进行中、评审中、验证中、待验收、完成。服务端约束进入/退出、产出和后继条件，每个工作包有唯一负责人及可选协作者。工作包检查项承载细分任务，当前不是每个检查项都有独立生命周期。

领导可调整优先级、WIP、SLA、修复额度和最低测试要求，保留策略版本、原因与历史。策略更新不清空已有工作，不可改列或绕过真实验收；成员变化作用于下一轮，保护运行快照。

取舍：采用可检查的流程而非无限自主调度。当前专业工作包仍串行，WIP 不等于并发；战略界面为策略编辑与审计记录，尚非独立战略卡片执行引擎。

以真实执行证据判断交付

模型输出文件或精确局部补丁，服务端检查路径、大小和唯一匹配后保存草稿。runner 用 esbuild 编译并在 Chromium 操作页面；团队额外经过独立源码审查与独立测试，通过后提交版本。

测试支持点击、输入、文字/可见性/禁用状态断言、真实刷新与隔离存储清理，最多 48 步。每次测试用新上下文，刷新保留该次 localStorage。失败仍阻止交付。

取舍：固定 React 依赖，不执行生成项目的任意安装脚本；runner 没有模型密钥或 Docker socket，测试拦截外部网络。云接口使用替身验证 UI，不代替真实账号、支付或数据服务验收。

先区分失败原因，减少无效返工

连接故障有限重试当前步骤；已有草稿时先复验，而非一律重新生成。交互或协议失败允许一次额外 QA 诊断，确认是测试错误才只改脚本，保存修改前后步骤与原因并真实重跑。应用缺陷进入开发修复，最多两次或策略配置的更低上限。

真实案例：习惯打卡应用曾卡在“点击空白输入下已禁用的添加按钮”。工程师取消禁用后，QA 又要求恢复，耗尽修复次数；原协议还缺少刷新，却要求验证持久化。补齐协议和分流后，复用同一份源码，31 步开发自测、34 步独立验收通过，覆盖打卡/撤销、100% 边界、重名、删除和刷新恢复。另在 1280、375、320 像素验证布局及两个习惯的总进度。

这是开发环境的一个真实回归案例，不代表所有需求的成功率，也不把草稿恢复速度当作从零生成性能。

连续的导航与数据体验

工作台共用侧边栏和项目缓存，切换团队/设置不重复加载近期项目。封面来自实际生成页面，已有封面最多六路并发读取，首次昂贵渲染单独排队；返回页面可复用有界缓存，账号切换会清理缓存。

取舍：优先快速显示已有封面，首次截图仍需渲染，不承诺全部首访瞬间完成；缓存有容量、过期和用户隔离约束。

单机可交付架构

前端 React/TypeScript/Vite，后端 FastAPI；SQLite 保存账号、项目、任务、源码和版本；独立容器运行 app 与 runner，Caddy 提供 HTTPS。Compose 降低部署和备份成本，模型凭据保留在后端。

换绑需第三方重新授权及显式选择；修改密码后轮换会话版本，使旧会话失效。生产和开发使用独立数据卷，升级先备份数据库及配套密钥。

取舍：目前没有分布式队列、多 worker 一致性、大规模容量或商业计费闭环保证。提高并发前需补齐持久调度与资源隔离。

验证与工程质量

后端在临时 SQLite 和模拟模型上验证权限、状态机、恢复和第三方协议；前端检查类型、缓存、账号切换及工作台逻辑；runner 使用实际 Chromium。真实模型案例和生产冒烟分别记录，避免把 mock 当作外部服务成功。

本次最终检查数量、生产版本和公开访问结果见发布验证记录。启动、测试命令见 README。

对评估维度的回应

  • 完成度：主链路可运行，生成应用可操作；账号隔离、恢复与版本保护有测试，未完成项明确列出。
  • 工程思维：固定状态机与策略分离，测试与应用错误分流，受控依赖、单机架构和局部补丁控制复杂度。
  • 用户体验：一致导航、真实封面、明确角色进度，失败后沿用成果，减少重复等待和误导。
  • 创新性：领导策略、专业直达与真实验收证据在同一工作台呈现；可配置伙伴和团队，不只展示多角色聊天。
  • 可交付性：公开 Demo/源码、启动命令、部署备份说明、版本记录和可复制流程模板。
